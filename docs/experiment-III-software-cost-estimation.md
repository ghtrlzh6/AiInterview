## 一、实验目的

1. 了解软件成本估算的基本思路，学会基于功能点分析（FPA）结果进行造价评估的完整流程。  
2. 结合本课程项目《AI 模拟面试与能力提升平台》的设计文档，使用 **GB/T 36964—2018《软件工程 软件开发成本度量规范》** 推荐的功能点方法度量软件规模，并据此估算开发成本和工期。  
3. 选用 **NESMA** 功能点方法对估算结果进行交叉验证，分析两种方法之间的差异及原因。  
4. 引用 **北京软件造价评估技术创新联盟（BSCEA）** 发布的行业基准数据，将功能点规模转换为工作量和费用。

## 二、实验原理

### 2.1 软件成本估算的地位

软件成本估算是软件工程管理和软件经济评价的基础。在项目立项、招投标、预算编制和验收审计等环节，都需要对软件开发的规模、工作量和费用给出可量化、可比较的估算结果。

### 2.2 功能点分析（FPA）

功能点分析从软件系统的**功能特征**出发来度量规模，与具体的实现语言、开发工具无关。主流方法包括 IFPUG、NESMA、GB/T 36964、COSMIC、MARK II 等，其中 IFPUG 与 NESMA 的市场占有率超过 90%，**GB/T 36964 方法与 IFPUG/NESMA 详细功能点法基本等价**。

功能点计数将系统功能划分为五类：

| 类型 | 英文缩写 | 含义 |
|------|----------|------|
| 内部逻辑文件 | ILF | 由本系统维护的用户可识别逻辑数据组 |
| 外部接口文件 | EIF | 由外部系统维护、本系统引用的逻辑数据组 |
| 外部输入 | EI | 从系统边界外输入数据并完成处理的事务 |
| 外部输出 | EO | 含计算、推导或格式化处理的输出事务 |
| 外部查询 | EQ | 不含推导计算的简单检索事务 |

各计数项按数据元素（DET）和记录类型（RET）或文件类型引用（FTR）判定低/中/高复杂度，再乘以对应权重得到**未调整功能点（UFP）**。

### 2.3 GB/T 36964 成本度量方程

依据国标及 BSCEA 团体标准 T/BSCEA 002 推荐的**方程法**：

$$\text{工作量（人时）} = \text{调整后规模（FP）} \times \text{生产率（人时/FP）} \times \text{软件调整因素} \times \text{开发调整因素}$$

$$\text{软件开发费用} = \text{工作量（人月）} \times \text{人月费率（元/人月）} + \text{直接非人力成本}$$

或直接采用功能点单价法：

$$\text{软件开发费用} = \text{调整后规模（FP）} \times \text{功能点单价（元/FP）}$$

### 2.4 基准数据来源

本实验采用 **《2024 年度中国软件行业基准数据》（CSBMK®-202410）**，数据由北京软件造价评估技术创新联盟发布，发布日期为 2024 年 10 月 31 日。

### 4.2 步骤二：选择生产率标准并估算工作量

#### 4.2.1 生产率选取

参照 CSBMK®-202410 全行业软件开发生产率中位数（P50）：

| 指标 | 数值 | 来源 |
|------|------|------|
| 开发生产率 P50 | **6.83 人时/功能点** | 表 4.1，CSBMK®-202410 |
| 电子政务 P50（参考） | 6.54 人时/功能点 | 表 4.2 |

本项目属于教育类信息化应用，基准数据中没有单独发布教育行业的数值，按照国标 FAQ 的说明，**采用全行业基准值**。

#### 4.2.2 工作量计算

$$\text{开发工作量} = 410 \times 6.83 = 2{,}800.3 \approx \mathbf{2{,}800 \text{ 人时}}$$

换算成人月（实验指导书推荐每月按 **22.5 个工作日**、每日 8 人时计算）：

$$1 \text{ 人月} = 22.5 \times 8 = 180 \text{ 人时}$$

$$\text{工作量} = 2{,}800 \div 180 = \mathbf{15.6 \text{ 人月}}$$

> 注：BSCEA 基准数据中人月按 21.75 天/月计算（174 人时/人月），得到 16.1 人月，与上面的结果接近。本报告以实验指导书推荐的 22.5 天/月为准。

#### 4.2.3 软件调整因素（补充说明）

依据 CSBMK®-202410 附录 A，本项目特征及调整因子如下：

| 调整因子 | 取值 | 依据 |
|----------|------|------|
| 业务领域 | 1.00 | 采用全行业基准生产率，不再叠加 |
| 应用类型 | 1.50 | 智能信息类（大模型、NLP、智能评估） |
| 完整性级别 | 1.00 | 无明确 A/B 级完整性要求 |
| 非功能性特征 | 0.975 | 分布式处理 0、性能 0、可靠性 0、多重站点 -1 |
| 开发平台 | 1.00 | Java/Spring Boot |
| 团队背景 | 1.20 | 无同类项目经验（学生团队） |

$$\text{综合调整系数} = 1.50 \times 0.975 \times 1.00 \times 1.20 = 1.755$$

$$\text{调整后工作量} = 15.6 \times 1.755 = \mathbf{27.4 \text{ 人月}}$$

**本报告主结果取调整前的基准工作量（15.6 人月）**，调整系数作为 AI 类项目的风险参考；如果计入调整系数，工作量约为 27.4 人月。

### 4.3 步骤三：换算日历工期

#### 4.3.1 按基准工作量估算

假设投入 **4 人全职** 开发（与本项目实际团队规模一致）：

$$\text{日历工期} = 15.6 \div 4 = \mathbf{3.9 \text{ 个月}} \approx \mathbf{4 \text{ 个月}}$$

按调整后工作量（含 AI 项目调整因子）：

$$27.4 \div 4 = 6.9 \text{ 个月}$$

#### 4.3.2 与实际开发计划对照

本项目开发计划为 4 人 × 8 周 ≈ **8 人月** 的实际投入，低于行业基准的 15.6 人月。主要原因有：

- 学生竞赛场景下部分功能采用了模拟 AI 降级方案，降低了 LLM 集成与测试的工作量；  
- 复用了 Spring Boot、Vue 3 等成熟框架，编码效率比行业平均水平高一些；  
- 部分加分项（Chroma RAG 完整向量化、远端部署等）还没有完全实现。

### 4.4 步骤四：获取软件成本

#### 4.4.1 方法一：功能点单价法

采用 CSBMK®-202410 北京市软件开发功能点单价基准：

| 参数 | 数值 |
|------|------|
| 调整后规模 | 410 FP |
| 北京功能点单价 P50 | **1,261.14 元/FP** |

$$\text{软件开发费用} = 410 \times 1{,}261.14 = \mathbf{517{,}067 \text{ 元}} \approx \mathbf{51.7 \text{ 万元}}$$

这个费用包含：直接人力成本、间接人力成本、间接非人力成本及合理利润（含税），**不含**直接非人力成本（比如专用硬件采购、云服务器租赁、DeepSeek API 调用费等）。

#### 4.4.2 方法二：人月费率法

| 参数 | 数值 |
|------|------|
| 工作量 | 15.6 人月 |
| 北京软件开发人月费率 P50 | **32,129 元/人月** |

$$\text{软件开发费用} = 15.6 \times 32{,}129 = \mathbf{501{,}212 \text{ 元}} \approx \mathbf{50.1 \text{ 万元}}$$

两种费用算法的差异率：

$$|51.7 - 50.1| \div 51.7 = 3.1\% < 20\%$$

结果互相印证，数值比较合理。

#### 4.4.3 直接非人力成本

| 项目 | 估算金额 | 说明 |
|------|---------|------|
| 云服务器（MySQL/Redis/Nginx） | 0.3 万元/年 | 学生开发期可以用本地 Docker 替代 |
| DeepSeek API 调用 | 0.2 万元 | 按评估与对话的 token 用量估算 |
| 域名与 SSL 证书 | 0.05 万元 | 可选 |
| **合计** | **≈ 0.55 万元** | 未计入上述 51.7 万元开发费 |

#### 4.4.4 含调整系数的参考造价

如果计入 AI 智能信息类项目的调整系数（1.755）：

$$51.7 \times 1.755 = \mathbf{90.7 \text{ 万元}}$$

这个数值更接近商业公司承接同类 AI 应用的报价区间，可以作为项目若进入正式采购时的上限参考。

### 4.5 步骤五：NESMA 方法交叉验证

#### 4.5.1 验证方法说明

**NESMA**（Netherlands Software Metrics Association）功能点法与 IFPUG/GB/T 36964 使用相同的五类功能划分和基本权重，主要差异在于个别事务的类型判定标准——NESMA 对 EO 的判定更为严格，要求输出必须包含**派生数据**（经过公式计算、算法处理或显著格式重组的数据），否则归入 EQ 或 EI。

#### 4.5.2 NESMA 重新计数差异项

| 功能 | GB/T 36964 分类 | NESMA 分类 | 调整 |
|------|----------------|-----------|------|
| 用户登录 | EQ（4 FP） | EI（4 FP） | 类型变更，点数不变 |
| 语音转文字 | EO（5 FP） | EI（4 FP） | EO→EI，-1 FP |
| AI 连通性测试 | EO（4 FP） | EQ（3 FP） | EO→EQ，-1 FP |
| 面试开场 LLM 生成 | EO（5 FP） | EI（4 FP） | EO→EI，-1 FP |
| SSE 流式对话 | EO（7 FP） | EI（4 FP） | EO→EI，-3 FP |
| 获取报告列表 | EQ（4 FP） | EO（5 FP） | 含分页聚合，EQ→EO，+1 FP |

两种功能点方法的结果高度一致，验证通过。

## 六、实验心得体会

这次实验把前几次课学的功能点计数真正用到了自己的课设项目上，感觉比做抽象例题要深刻得多。

第一，功能点计数要抓住“用户可感知的功能”，不能简单地数API或数据表。一开始我们倾向于按19张数据库表数ILF，后来发现像t_interview_question、t_chat_message这些表都应该归到“面试会话”这一个逻辑文件里，否则规模会被严重高估。这说明 FPA 的核心是业务逻辑分组，不是物理表一一对应。
第二，EO 和 EQ 的边界最容易出分歧。比如 SSE 流式对话，按照GB/T 36964算EO（因为包含了 LLM 推理与追问策略），而NESMA下更倾向算EI（因为主要是维护对话记录）。这次两种方法只差2个功能点，但如果团队对EO判定标准不统一，差异可能会拉大。我们在实验过程中专门对照接口说明，逐条标注是否存在“派生数据”，才避免了随意分类。
第三，行业基准数据让“规模”真正变成了“钱和时间”。373功能点本身没什么直观感受，但乘以 6.83人时/FP得到15.6人月，再乘以32,129元/人月的人月费率，得出约 50 万元。这个数字对项目管理者来说才有决策意义。我们也注意到，学生团队8周的实际投入大约8人月，远低于行业基准，这说明基准数据反映的是包含完整需求、设计、测试、项目管理在内的商业项目全生命周期成本，不能直接等同于课设投入。
第四，AI 类项目的调整因子值得关注。CSBMK 基准数据将“智能信息”类应用的生产率调整因子定为1.5，计入后造价接近91万元。这提醒我们：集成大模型、RAG、多维度评估的系统，其真实商业成本比普通CRUD管理系统高不少，立项预算时不能简单按表格式系统去估算。
第五，两种方法交叉验证非常有价值。 本次GB/T 36964与NESMA差异不足1%，增强了对估算结果的信心。如果差异超过20%，就需要回头检查ILF分组、EO/EQ分类是否存在系统性偏差，必要时引入第三方评审或COSMIC方法从“数据移动”角度做第三方仲裁。

## 七、思考题

**题目：若两种软件成本估算方法的结果差异显著（大于 20%），准备采用哪些方法解决？**

如果出现显著差异，我们小组会按以下步骤处理：

1. **回溯规模计数清单，统一计数边界。** 召集组员对照同一份需求文档，逐条核对 ILF 分组是否一致、有没有遗漏或重复计数的事务，重点复查 EO/EQ 分类和复杂度判定（低/中/高）。

2. **组织正式评审会议。** 参照 GB/T 36964 及 T/BSCEA 002《软件造价评估实施规程》，请没有直接参与计数的同学或指导教师担任评审员，对分歧项逐条讨论并表决，形成评审记录。

3. **引入第三种方法仲裁。** 如果 IFPUG 与 NESMA 还是无法收敛，可以引入 **COSMIC 功能规模测量方法**（按 Entry/Exit/Read/Write 数据移动计数），或者采用 **COCOMO II 模型**以代码行数或对象点做辅助校验，从不同于功能点的维度交叉验证。

4. **利用专业工具减少人为偏差。** 使用 BSCEA 认可的造价评估工具（如智估星等），将 api-design.md 结构化导入，让工具按统一规则自动计数，再与手工计数结果进行比对。

5. **取合理区间而非单点值。** 如果经过多轮评审后仍然存在不可消除的分歧，就在报告中同时给出 P25 与 P75 生产率下的费用区间（CSBMK®-202410 全行业生产率 P25=3.88、P75=12.39 人时/FP），用区间估算代替单点估算，并在立项文件中明确说明假设与风险。

6. **追溯调整因子假设。** 检查应用类型、团队经验、非功能性特征等调整因子是不是有一方取值过高或过低，特别是 AI 类项目的 1.5 倍应用类型因子是否适用，必要时参考已有类似项目的实际结算数据来做校准。
